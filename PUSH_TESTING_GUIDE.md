# Руководство по тестированию Push-уведомлений (Backend)

## Как это работает

- Сервис импорта запускается по cron (`CRON_SCHEDULE`) или вручную через endpoint (`POST /jobs/import-orders/run`).
- Во время импорта бэкенд определяет **только новые грузы** (ветка `create` в `runOrdersImport`).
- Push-уведомления отправляются **только при триггере cron**.
- Получатели уведомлений:
  - владелец груза (пользователь, на которого создан заказ);
  - пользователи, у которых id владельца указан в `linkedUsersIds`.
- Payload пуша формируется по фиксированному контракту (см. блок ниже).

## Payload contract (app ↔ server)

Для уведомления о новых отправках backend отправляет `data`:

- `screen` (required): `"shipments"`
- `sort` (optional): `"new" | "old"` (сейчас `"new"`)
- `filter` (optional): `"active" | "finished" | "wait" | "paid"` (сейчас `"active"`)
- `newOrdersCount` (optional): строка с числом новых отправок (`String(count)`)

Правила:

- `screen` обязателен, иначе приложение скипнет навигацию;
- значения `sort`/`filter` должны быть только из допустимых enum;
- `newOrdersCount` всегда отправляется как строка, совместимая с `parseInt`.

## Тестирование в dev

### 1) Подготовка тестовых данных

- В документах Firestore `users` убедитесь, что:
  - у каждого пользователя поле `id` совпадает с id при логине в приложении;
  - у части пользователей заполнен `linkedUsersIds`;
  - у целевых пользователей есть карта `pushTokens` (собирается из приложения).
- В тестовой Google-таблице добавьте новую строку с уникальным `Номер накладной` и валидным `КОД`.

### 2) Локальный запуск бэкенда

```bash
cd server
npm install
npm run dev
```

### 3) Запуск импорта для проверки

- Ручной запуск (импорт должен пройти, но push **не** отправляется — так задумано):

```bash
curl -i -X POST "http://127.0.0.1:4000/jobs/import-orders/run" \
  -H "x-job-token: <JOB_TOKEN>"
```

- Проверка поведения cron в dev:
  - временно задайте частое расписание в `.env` (например, каждую минуту):
    - `CRON_ENABLED=true`
    - `CRON_SCHEDULE=* * * * *`
  - подождите 1–2 минуты и смотрите логи.

### 4) Проверка результата

- В логах должно быть:
  - старт и завершение импорта;
  - статистика created/updated;
  - счётчики пушей (`pushRecipients`, `pushNotificationsSent`) при запуске по cron.
- В Firestore должны появиться созданные заказы.
- На целевых устройствах должен прийти push.

## Чеклист поведения в production

- Push отправляется только когда:
  - триггер — `cron`;
  - есть хотя бы один **новый** созданный груз.
- Push **не** отправляется когда:
  - импорт ручной;
  - были только обновления существующих грузов;
  - новых грузов нет.

## Диагностика проблем

1. **Новые грузы создались, но пушей нет**
   - Проверьте триггер: должен быть cron.
   - Проверьте, что у пользователя есть `pushTokens` в Firestore.
   - Проверьте связи через `linkedUsersIds` у нужных документов users.

2. **Импорт успешен, но получателей 0**
   - Убедитесь, что `КОД` в строке таблицы соответствует существующему пользователю.
   - Проверьте согласованность id (`users.id` в документе и id, под которым логинится приложение).

3. **Ошибки FCM в логах**
   - Невалидные/отозванные токены удаляются автоматически.
   - Убедитесь, что Firebase Admin service account и проект совпадают с проектом мобильного приложения.

4. **Push приходит, но приложение скипает обработку**
   - Проверьте `data.screen` — должно быть `shipments`.
   - Проверьте, что `sort`/`filter` в допустимых значениях контракта.
   - Проверьте, что `newOrdersCount` сериализуется строкой (например `"3"`).

5. **Cron не запускается**
   - Проверьте `CRON_ENABLED=true`.
   - Проверьте `CRON_SCHEDULE` и `CRON_TZ`.
   - Убедитесь, что процесс жив (health endpoint и логи на Railway).

## Финальный QA checklist (backend + contract)

- Cron-импорт с новыми грузами отправляет push; ручной импорт push не отправляет.
- В `data` всегда присутствует `screen=shipments`.
- `sort` и `filter` отправляются только в допустимых значениях контракта.
- `newOrdersCount` сериализуется строкой (`String(count)`).
- Для одного пользователя на нескольких устройствах push уходит на все `pushTokens`.
- Невалидные FCM-токены удаляются автоматически из `pushTokens.<deviceId>`.
- Метрики в логах (`pushRecipients`, `pushNotificationsSent`) соответствуют фактической рассылке.
